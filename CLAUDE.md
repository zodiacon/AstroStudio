# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AstroStudio is a native Windows desktop astrology application built with C++20, WTL (Windows Template Library), and Direct2D/DirectWrite. It calculates and draws natal/chart data (planets, houses, aspects) using the Swiss Ephemeris library.

## Build

This is a Visual Studio solution (`AstroStudio.sln`), not a CMake/cross-platform project. Build with MSBuild or Visual Studio 2022+ (toolset v145, targets Win32/x64/ARM64, `stdcpp20`).

```
msbuild AstroStudio.sln /p:Configuration=Debug /p:Platform=x64
```

There are no lint configs or CI workflows in this repo. `AstroCore` has unit tests (below); everything else is verified by building and running the app (`x64\Debug\AstroStudio.exe`).

### Tests

`AstroCore.Tests` is a Catch2 v3 console project (x64 only, Debug and Release) covering `AstroCore`: `DateTime`, `AstroPoint`, `Aspects`, `AstroCalculator` (positions, houses, ingresses, stations - checked against equinox times, J2000 and the 2024 Mercury retrograde, using the built-in Moshier ephemeris so no data files are needed) and `ChartData`. Build the solution, then run `x64\Debug\AstroCore.Tests.exe` (`[DateTime]` etc. select by tag; the exit code is 0 when everything passes).

- Catch2 comes from vcpkg in classic mode (`E:\vcpkg`, integrated with MSBuild). The project uses the `x64-windows-static` triplet (`VcpkgUseStatic`) because AstroCore and sweph use the static CRT (`/MT`); `VcpkgAutoLink` is off and Catch2 is linked explicitly (`Catch2Main` lives in `lib\manual-link`). The solution's x86 configuration doesn't build it (no x86 Catch2 installed).
- To record a bug you haven't fixed yet, write the test for the correct behaviour and tag it `[!shouldfail]` (Catch2 counts a failure as a pass and starts complaining when the bug is fixed - then remove the tag). There are none at the moment.
- `DateTime::Get` works in whole milliseconds on purpose: splitting the day fraction with doubles made a whole minute read back as the previous minute plus 59.99999 seconds. `AstroPoint::MidPoint` is the midpoint on the shorter arc, and `IsBetween(start, end)` is the range running forward from `start` to `end`, through 0 Aries if `end` is the smaller number.

### Submodules

`WTLHelper` is a git submodule (https://github.com/zodiacon/WTLHelper). Run `git submodule update --init` after cloning if it's empty.

## Solution structure

The `.sln` builds five projects: `AstroStudio` (the app), `AstroCore` (calculation engine), `sweph` (Swiss Ephemeris, vendored C library), `WTLHelper` (submodule, shared WTL UI helper library used across the author's other projects) and `AstroCore.Tests` (Catch2 tests for `AstroCore`, below). There were once `CairoGfx` and `QChart` alternative rendering backends in the repo; they were unused and are gone (the app draws with Direct2D).

- **`sweph/`** — Vendored Swiss Ephemeris C sources (`swe*.c/h`). Treat as third-party; avoid modifying unless fixing a vendoring issue. **One deliberate change**: `sweodef.h`'s `TLS` macro was empty under Visual C++ (it excluded `WIN32`), so the library's state (`swed`) was one global shared by every thread and two threads calculating at once corrupted each other; the condition now lets `_MSC_VER` through, so the state is `__declspec(thread)` and each thread has its own. Because of that `AstroCalculator::s_init` (setting the ephemeris path, which the Chiron/asteroid files need) is `thread_local`, so every thread that calculates sets it once. `CalculatorTests` has a four-thread test that fails without the change - keep it passing if the library is ever re-vendored.
- **`AstroCore/`** — Platform-agnostic astrology calculation engine, no UI/WTL dependencies.
  - `DateTime` — Julian day based date/time type (Gregorian/Julian calendar aware).
  - `AstroPoint` — zodiac position type; `Planet`, `ZodiacSign` enums.
  - **Aspect settings** (`AspectSettings` in `Aspects.h`): the general orbs (`MajorAspectOrb`, `MinorAspectOrb`, `ConjunctionOrbAdd`, `MajorOnly`, and the old Sun/Moon extras), plus per aspect an on/off switch and an orb of its own (`AspectEnabled`, `AspectOrb`, negative = use the general one; `OrbFor`) and per planet an on/off switch and an extra orb (`PlanetEnabled`, `PlanetOrbAdd`; the larger of the two planets' extras applies). A disabled planet takes part in no aspect (`Calculate` skips it; the aspect grid still lists it).
  - `DerivedCharts` (`DerivedCharts.h`) — charts worked out from other charts, and the calculations behind them (no UI; the groundwork for progressions, returns, composites and synastry). **Progressions and directions**: `Progress(calc, natal, target, options)` by `ProgressionMethod` - *Secondary* (a day for a year: planets at natal time + years-as-days, `ProgressedTime`; angles by `ProgressedAngles`: calculated for the progressed moment, the birth MC moved by the solar arc, or natal), *Primary* (planets stay; the ARMC advances by years x arc and the houses come from `CalcHousesFromArmc`) and *SolarArc* (every planet and angle moved by the arc). The arc is `Arc(...)` by `ArcKey`: the true distance the progressed Sun has moved (`Actual`, solar arc only; primary uses Naibod then), Naibod 0.98564736 deg/yr or Ptolemy 1 deg/yr. `Info().Time` of the result is the moment whose sky the planets are at (progressed moment for secondary, birth for the others). Years are tropical (`TropicalYear`). **Returns**: `FindLongitude`/`FindReturn` find when a planet is at a longitude (next/previous/nearest; steps of a few degrees then bisection; a retrograde planet can pass a longitude several times and each counts). **Composite**: midpoints on the shorter arc, averaged speeds, houses for the midpoint place and time (`CompositeHouses`: midpoint MC or midpoint ARMC). Helpers: `HousesFromMC`, `HouseOf` (a house is [cusp, next cusp): a planet on a cusp is in the house that begins there), `HouseOverlay`; and `AspectCalculator::CalcBetween` for the aspects between two sets of planets. `AstroCalculator` gained `CalcHousesFromArmc` and `Obliquity`. Wired into the UI: secondary progressions and solar arc directions (overlays), returns, composites and Davison charts (`Chart > New Derived Chart`); primary directions are not (they move only the angles). `Davison(calc, a, b)` casts an ordinary chart for the midpoint of the two times and places (`MidpointInfo`, which `Composite` uses too).
  - `Analysis` (`Analysis.h`) — scans a range of dates for the events between a birth chart and the sky or its progressions (no UI; the engine of the planned Analysis view). `Analysis::Run(calc, natal, AnalysisSettings, progress)` returns time-ordered `AnalysisEvent`s (`Time` UT, `Kind`, `Mover`, target planet or natal Asc/MC, `Aspect`, `Orb`, `Pass`, `Retrograde`, `Index`, `Longitude`). `AnalysisType`: transits to natal, progressed to natal, solar arc to natal, transits to progressed, progressed to progressed. **Event kinds**: for every aspect *Enters orb / Exact / Leaves orb* (or *In orb at start/end* if the range begins or ends inside the orb), *House ingress* (through the natal cusps; natal-target types only), *Sign ingress* and *Stations*. `Pass` numbers the times a retrograde planet makes the same aspect (1-3; it starts at each enter). **`AnalysisEvent::Window`** (`AnalysisWindow`: `HasEnter`/`Enter`, `Exacts`, `HasLeave`/`Leave`) is set on the one event that *ends* each stay within an orb - the *Leaves orb* row, or *In orb at end* - with the whole stay, gathered in `Scan::Finish` by a per-(mover, target, aspect) walk through the sorted events; a stay that was under way when the range began has no enter, one still on at its end has no leave, and a planet turning inside the orb gives several exacts in one stay. The orb is `AspectCalculator::MaxOrbFor(type, mover, target)` (the aspect's orb plus the planets' extras; only the mover's for an angle; negative if the aspect or a planet is off), so the aspect settings apply as everywhere else. **`EffectiveMovers()` drops the Moon from transits when the range is over `MoonTransitLimitDays` (62)**; progressed and solar arc Moons stay. **Method**: everything is *the same crossing problem* - per mover, sample its longitude with a step of a fraction of the smallest orb (relative to its speed plus the fastest moving target's, 0.001 to 20 days) and watch `Wrap180(mover - reference - delta)` for each target, aspect (both `delta = +angle` and `-angle`, except the conjunction and opposition) and, for ingresses, each fixed longitude (cusp, sign start). A sign change is *Exact*, the absolute value crossing the orb is *Enter/Leave*, both located with Illinois false position on exact ephemeris values (tolerance 1e-8 degrees). A speed sign change between two samples splits the step (and is a *Station*), so an orb that a planet touches and turns back from is not missed. Progressed and solar arc positions come from `Source`s (`TransitSource`, `ProgressedSource`, `SolarArcSource`) - the slow ones are read through a 10-day grid with cubic Hermite interpolation (`Series`) while scanning and pinned down exactly afterwards; in progressed-to-progressed each pair is looked at once (mover before target in `Planet` order). **Several analyses together**: `Analysis::RunAll(...)` runs one `Run` for each of `AnalysisSettings::TypeList()` (`Types`, or just `Type`), tags every event with its `AnalysisEvent::Type`, merges them in time order, and spreads the progress over them; sign ingresses and stations are wanted once per kind of mover (sky, progressions, solar arc), so a later analysis with the same kind of mover leaves them out (two transit analyses would otherwise list every station twice), and each analysis applies its own Moon rule. Rough Debug-build cost with every planet as mover and target and every aspect at default orbs: ten years of transits 3.6 s (43,000 events), eighty years of progressions 1-2 s; run it on a worker thread and use the progress callback (returns false to cancel).
  - `Midpoints` (`Midpoints.h`) — midpoints between points of a chart (no UI, not wired into the UI yet). A `ChartPoint` is a planet (`Body`) or the Ascendant/Midheaven (`PointKind`) with its longitude and speed (`SameAs` compares kind and body only); `Midpoints::Points(chart, MidpointOptions{Angles, Only})` collects them from a chart (angles only if asked, from `Houses()`). `Midpoints::Calculate(points)` gives a `MidpointData` (`A`, `B`, `Longitude` on the *shorter arc* like `AstroPoint::MidPoint`, `Speed` the mean of the two, `Arc` the distance between the ends, `Opposite()` the far midpoint on the same axis) for every unordered pair, sorted by longitude; `CalcBetween(a, b)` does each of one set with each of another (two charts; the same planet in both is a pair). **Contacts**: `Midpoints::Contacts(midpoints, points, ContactOptions)` lists the points standing on a midpoint - `ContactKind::Axis` (0 and 180 degrees from it) or `Dial90` (Ebertin's 90-degree dial: also 45, 90 and 135), within `Orb` degrees (1.5 default), tightest first (`MidpointContact`: index of the midpoint, the point, the `Angle`, the `Orb`). A point is never a contact of a midpoint it is one end of (`ExcludeMembers`; at 45 degrees it always would be for a 90-degree arc) - turn that off when the midpoints and the points are from different charts. `OnDial(longitude, divisions)` is the position on the 360/n-degree dial (n=4: the 90-degree dial used to line up a midpoint tree) and `ContactOrb` the distance measure behind the contacts. Tests: `MidpointTests.cpp`.
  - `ArabicParts` (`ArabicParts.h`) - Arabic parts (lots) of a chart, no UI and not wired into the UI yet. A part is `Base + Plus - Minus` (`PartDefinition`; each a `PartPoint`: a planet, Asc/MC/Desc/IC, a house cusp, the *ruler of* a house cusp - where that planet is in the chart - or another part by name, which must come earlier in the list), and with `PartReversal::AtNight` Plus and Minus change places in a night chart. `ArabicParts::Standard()` is a starting set (Fortune, Spirit, Eros, Courage, Victory, Nemesis, Father, Mother - each "from X to Y" = Asc + Y - X, reversed at night, in Hellenistic form - and Lilly's Marriage and Death, which don't turn round); the sources differ on many of these, so treat it as definitions to change or add to. `Calculate(chart, definitions, PartOptions)` goes through the list in order (so a part can use one before it) and leaves out a part whose points the chart lacks (a planet it doesn't have); the result is `PartData` (`Longitude`, `Night`, `Reversed`, `House` via `DerivedCharts::HouseOf`, and the `Formula` as used, "Asc + Sun - Moon"). **Sect**: `IsDay(sun, asc)` - the Sun is up from the Descendant forward to the Ascendant (houses 7-12); `IsDayChart` uses the chart's Sun (nothing if it has none, which counts as day); `PartOptions::Sect` can force day or night, `ReverseAtNight` off stops all turning round, `ModernRulers` gives Scorpio/Aquarius/Pisces to Pluto/Uranus/Neptune (`Ruler(sign, modern)`). **Aspects to planets**: `ArabicParts::Aspects(parts, planets, AspectCalculator)` gives the `PartAspect`s (part index, planet, type, angle, orb, `MaxOrb`) - a part isn't a planet, so the orb is the aspect's own plus the planet's extra (`MaxOrbFor(type, planet, nullopt)`, which also honours the on/off switches and `MajorOnly`), one aspect per pair (the first that fits, major first) and no applying/separating, a part having no speed. **The Part of Fortune among the planets** (`Options > Show Part of Fortune`, `ID_OPTIONS_FORTUNE`, `AppSettings::ShowPartOfFortune`, off by default; `IView::PartOfFortuneChanged` reaches every page): `Planet::PartOfFortune` (after Vesta, glyph ⊗ = code 60 of the font, name "Part of Fortune") is a *point*, not a body: `AstroCalculator::CalcPlanet` never asks the ephemeris for it (the number would be one of the ephemeris's own) and returns zeros, and `ChartData::UpdatePartOfFortune(calc)` works it out - by day Asc + Moon - Sun, by night Asc + Sun - Moon (sect by the real Sun; in a harmonic chart the harmonic of the real place) - when the chart has the point among its planets *and* a Sun and Moon. It is called at the end of `AstroCalculator::Calculate`, `ChartData::CalcPlanets` and `CalcHouses`, `DerivedCharts::Progress` and `Composite` (Davison goes through `Calculate`), so it follows Step, Live and progressions. **The option is a view matter, not the chart's**: `CChartView::SyncPartOfFortune` adds the point to (or removes it from) the chart's planets when a chart is set and when the option changes - the details list, the wheel (glyph, dot, tip, the wheel options can hide it; `IDD_WHEELOPTIONS` is tall enough to list every body without scrolling, since a list that scrolled hid the last ones) and the print-out then show it like a planet - and it is *not saved* in `.chart` files (`ChartFile::Save` leaves it out), left out of a transit overlay (it needs the chart's Ascendant), of the analysis and ephemeris body lists and of the midpoints, and it makes **no aspects by default** (`AspectSettings::PlanetEnabled` for it starts off; the Aspects dialog lists it so it can be switched on). Tests: `ArabicPartsTests.cpp` (a hand-made chart with known answers, plus a real chart checked for sect against the Sun's house).
  - `AstroCalculator` — thin wrapper over `sweph` for planet positions, house cusps, ingresses, stations, eclipses (`CalcEclipses`, from `swe_sol_eclipse_when_glob`/`swe_lun_eclipse_when`) and the Moon's void of course periods (`CalcVoidOfCourse`: from the last exact conjunction/sextile/square/trine/opposition to the Sun and planets - through Pluto unless `outerPlanets` is off - until the Moon leaves its sign; found by stepping two hours at a time and bisecting the last crossing, and if there is none the void is the whole stay in the sign, `WholeSign`).
  - `ChartData` — the aggregate for one chart: planets, houses, harmonic, `ChartInfo` (person/event birth data). `CalcHouses`/`CalcPlanets` populate it via an `AstroCalculator`.
  - `Aspects.h` — `AspectCalculator` computes aspects (conjunction, trine, square, ...) between planet positions from `AspectSettings` (orbs).
- **`AstroStudio/`** — The WTL application.
  - `MainFrm` (`IMainFrame`) — main frame window; owns a `CNativeCustomTabView` hosting one tab per open chart. Creates new chart views via `AddChartView`.
  - `ChartView` (`CChartView`) — one chart's tab content; splits between `ChartDetailsView` (text/list data) and `GraphicChartView`.
  - `GraphicChartView` (`CGraphicChartView`) — renders the circular chart wheel via `D2DChartDrawing` onto its own `ID2D1HwndRenderTarget`.
  - `D2DChartDrawing` — Direct2D/DirectWrite drawing logic for the chart wheel (zodiac belt, houses, aspect lines) in a 1000x1000 logical space, parameterized by `ChartDrawingParameters` (colors, widths, toggles). `Draw` does not call `BeginDraw`/`EndDraw`; the owning view does.
  - **Dark mode for the wheel**: `ChartDrawingParameters` holds every colour the wheel uses (including `TextColor`, `GridColor` and `DotColor` - nothing is hard-coded in `D2DChartDrawing.cpp`), and `ChartDrawingParameters::Dark()` is the dark set. `CGraphicChartView::ApplyState` picks the set by `WTLHelper::IsDarkMode()` on every paint and every export/copy (so pictures follow the mode on the screen), and repaints on `ThemeChangedMessage`. The aspect grid takes its colours from the same source: `CAspectGridWnd::Refresh` builds the wheel's parameters for the look (with the user's `ChartColors` on top) and copies the background, house-line (grid), text and soft/hard/other aspect colours from them, so it is of a piece with the wheel and follows Options > Chart Colors (`CChartView::WheelOptionsChanged` refreshes it).
  - **Options > Always On Top / Font**: Always On Top is `WS_EX_TOPMOST` (kept in `AppSettings::AlwaysOnTop`, applied in `OnCreate`). Font chooses the *text* font - what is not astrological symbols, which are always HamburgSymbols - kept as a LOGFONT in `AppSettings::TextFont` (lfHeight in tenths of a point; empty face means Consolas). The ephemeris and the analysis view use it for their lists (`CreateFonts`, `IView::TextFontChanged`; its size becomes theirs, which their A+/A- buttons change), and the chart view applies it to the details view (`CChartDetailsView::ApplyTextFont`: the fields and labels take the family and at most 9 points, since a dialog's controls don't move; the two lists take the chosen size plus a fifth, and their columns grow with it), the aspect list (`CAspectListView::ApplyTextFont`) and, through `D2DResources::TextFontFamily`, every DirectWrite text that isn't a glyph: the aspect grid's orbs and the overlay caption. Nothing changes until the user has chosen a font (`Helpers::UserTextFont` is false then), so the defaults stay as designed; new views apply it as they are created. Fixed-width list columns ignore `SetColumnWidth`, so widths go through `Helpers::SetColumnWidth`.
  - **Interactive wheel** (`CGraphicChartView` + `D2DChartDrawing`): hovering a planet or an aspect line shows a tracking tooltip (`PlanetTip`/`AspectTip`: position, house, speed, the planet's aspects; orb and applying/separating for a line); clicking a planet highlights it and fades every aspect that isn't its own (click it again, or an empty spot, to let go); dragging turns the wheel (`Rotation`, degrees counterclockwise, default 0 = ascendant at the left; two quick clicks on an empty spot turn it back). Picking and rotation belong to the view, not the chart, and show in copies and exports. `D2DChartDrawing` records where it put planets and aspect lines during `Draw` (`m_planetSpots`/`m_aspectLines`), and `HitTest` works from those in the 1000x1000 space, so it only knows what the last `Draw` drew. Every angle in the drawing goes through `PointByAngle`, which applies the rotation; the zodiac belts use screen angles and subtract it separately. Clicking the wheel takes the keyboard focus so Ctrl+C copies the picture. `CGraphicChartView::Refresh` keeps a planet's tooltip (with new values) but drops an aspect's, since aspect indexes change. The tooltip window is only touched when its text or position changes (`ShowTip`): re-setting the same text, or moving to the same place, makes it repaint, which flashed on every mouse move and Live tick. It is created lazily, so the dark style is applied each time it is shown (`DarkMode::setDarkTooltips`) - the program can change modes while it exists.
  - **Overlays** (`Chart > Overlay`: None / Transits / Secondary Progressions / Solar Arc Directions / Synastry...; the toolbar's `Overlay` button (`ID_CHART_OVERLAY`, `BTNS_WHOLEDROPDOWN` + `BTNS_CHECK`, checked while any overlay shows) drops down the same choices, built in `OnOverlayDropDown` on `TBN_DROPDOWN` and marked from the same state, and its choice arrives as the menu items' commands; `ID_CHART_TRANSITS`, `ID_CHART_OVERLAY_*`; choosing what is already shown does nothing; `CChartView::ShowOverlay`/`HideOverlay`/`UpdateOverlay`/`UpdateOverlayUI`): the wheel can show a second set of planets around the chart - a `ChartOverlay` (`ChartOverlay.h`: `Kind` (`OverlayKind` Transit/Progressed/Synastry), `Method` (for Progressed: secondary or solar arc; primary directions move only the angles, so they have no planets to overlay), `When`+`Zone` (the moment, see below), `Data` (a second `ChartData`), `Aspects`, `Caption`, and the `Label`/`BaseLabel` used in tips: "Transit Sun ... natal Mercury", "Progressed ...", "Directed ...", or the two charts' names for synastry). **`When` is what Step, Auto and Live move while an overlay with a time (`OverlayHasTime()`: transits and progressions) is shown**; it starts as the current time in the chart's zone, and `UpdateOverlay` works the planets out from it: transits are the sky at `When` (`CalcPlanets`), progressions are `DerivedCharts::Progress(natal, When)` (caption adds the age, or the solar arc). **Editing the moment**: `Chart > Overlay > Set Date and Time...` (`ID_CHART_OVERLAY_DATE`, also the last item of the toolbar's Overlay drop-down; enabled only while `OverlayHasTime()`; `CChartView::OnOverlayDate`) opens `CDirectionsDlg` with `HideArc()` (the directions dialog without the arc combo - the buttons move up into its place) on the overlay's `When` shown in its `Zone`, and OK sets both, ends Live (the user took over the time) and recalculates through `UpdateOverlay`; the chart's own time is untouched and it isn't marked modified. A synastry overlay has no time: it is a *copy* of another open chart (`IMainFrame::OpenCharts(except)` collects them through `IView::GetChart`; several open -> a popup menu at the cursor, none -> a message), a snapshot that doesn't follow later edits or closing of the other chart, and Step/Auto/Live then act on the chart itself. The overlay kind is not saved. All kinds use the `Transit` aspect set of `AspectOptions` (shown in the options dialog as "Transit / overlay aspects"). The chart view owns it as `std::optional<ChartOverlay> m_Overlay` (engaged = shown) and hands a pointer to `CGraphicChartView::SetOverlay`/`ClearOverlay` and on to `D2DChartDrawing::Overlay`; the owner refreshes after changing it. The wheel becomes a bi-wheel - the chart shrunk to `BiWheelScale` (0.87, a transform about the center in `D2DChartDrawing::DrawChart`, so natal glyphs shrink too) inside a band holding the overlay's planets (glyphs at r=468, dots at r=441, in a band 62 wide, in `OverlayColor`) and the caption. For transits `Data` has the chart's planets, place and zone, starting at the current time; it is planets only (no houses) and the natal harmonic applies. The overlay's aspects to the chart's planets (`AspectCalculator::CalcBetween`, overlay = Planet1, chart = Planet2; the `Transit` set of `AspectOptions`: major aspects only, 3 degrees by default; computed in `UpdateOverlay`) are drawn as lines from an overlay dot to the natal dot, 0.5 to 2.5 wide by how close to exact they are against the widest orb allowed for that pair (`AspectData::MaxOrb`, set by `CalcAspect`: the aspect's orb plus the planets' extras), and the natal chart's own aspects are not drawn while an overlay shows. **Step, Auto and Live move the overlay's time while it is shown (`StepTime`/`TickLive` pick the target); the chart keeps its own time**, so none of it marks the chart modified. Hit testing knows four things (`ChartHit::Kind`: Planet, Aspect, OverlayPlanet, OverlayAspect) and a highlight is a `ChartSelection` (planet + whether it is the overlay's), so a natal and an overlay Sun can be told apart. The aspect list, like the wheel and the grid, shows only the overlay's aspects while one is shown (`SetOverlayAspects`/`ClearOverlayAspects`; the rows say "Transit Sun" ... "natal Mercury" by the overlay's `Label`/`BaseLabel`); the **aspect grid** follows the overlay: with one shown it is the overlay's planets down the side (glyphs in `OverlayColor`, the overlay's `Label` small in the corner) against the chart's along the top, with the overlay's aspects between them (`AspectGridDrawing::Overlay`, `CAspectGridWnd::SetOverlay`, fed by `UpdateOverlay`; looked up by *ordered* pair, so the same planet on both axes - a transit Sun on the natal Sun - is a cell like any other, and the chart's own aspects are not shown then). It is no longer square (`GridSize`/`NaturalSize` are a `SIZE`); without an overlay it is the symmetric grid of the chart's planets as before. Chart files know nothing about overlays.
  - **New derived charts** (`Chart > New Derived Chart`: Solar Return, Lunar Return, Solar Arc Chart..., Composite..., Davison...; `ID_CHART_DERIVED_*`, `CChartView::OnDerived`; enabled only for a chart that isn't itself read-only). **Returns** (`NewReturnChart`): `DerivedCharts::FindReturn(..., Nearest)` for the Sun or Moon from a reference moment - the overlay's `When` if a transit/progression overlay shows (so Step/Auto move where the search starts), otherwise now - then `IMainFrame::NewChartWithDialog(&info, &houseSystem)` opens the ordinary New Chart dialog prefilled with that moment, this chart's place, zone and house system and a name like `<tab title> Solar Return 2027`; the user can change the place (a return is often cast where the person is then) before OK, and the result is an ordinary editable, saveable chart. **Solar arc chart** (`NewSolarArcChart`): `CDirectionsDlg` (`IDD_DIRECTIONS`: date, time and zone with the shared `CTimeControls`, and the yearly arc - true solar arc, Naibod or Ptolemy) asks for the date, starting from the overlay's moment if a time overlay shows and otherwise now in this chart's zone; `DerivedCharts::Progress(..., SolarArc)` then moves every planet and angle (and the house cusps) by the arc and the result opens like a composite, read-only, named `Solar Arc yyyy/mm/dd: <tab title>`. Its details view shows the *birth* date and place (only the points move). The same dialog can serve secondary progressed and primary direction charts later. **Composite and Davison** (`NewPairChart`): the other chart is chosen with `PickOtherChart` (the same popup as synastry) and the result goes to `IMainFrame::AddDerivedChartView`, a **read-only chart**: `CChartView::DerivedChart` sets `m_ReadOnly` and skips the `calc.Calculate` that `Chart()` does (it would replace a composite's midpoints), `CChartDetailsView::SetReadOnly` disables every field and button but the two lists (re-applied after every `UpdateControls`, since setting the time re-enables the zone controls), `OnRecalc` only refreshes the aspects, Save/Save As are disabled, progression overlays and the derived-chart items are off, and Step/Auto/Live are disabled unless a transit overlay shows (`CanMoveTime()`; they then move the overlay's time, `StopTimeIfFixed` stops them when it goes). **Saving**: a derived chart is saved as its *recipe* (`DerivedRecipe` in AstroCore: `Kind` Composite/Davison/SolarArc, the source chart(s) `A`/`B` - only their details, positions are recalculated - and for a composite the `Houses` method, for a solar arc the `Target` date, its `Zone` and the `ArcKey`); `DerivedCharts::Build(calc, recipe)` makes the chart from it (unit-tested against making them directly), and it is the *only* way the views make these charts, so a chart made anew and one loaded from its file are the same. `CChartView` keeps `m_Recipe`; File > Save / Save As are enabled for a read-only chart that has one and write `ChartFile::SaveDerived`, and `CMainFrame::OpenChartFile` (`ChartFile::LoadFile`) opens such a file with `AddDerivedChartView(data, title, &recipe, path)`. The file format is below. `AddChartView` and `AddDerivedChartView` both rely on the frame calling `PageActivated` when a page is added, before the view knows it is read-only, so `DerivedChart` calls it again.

  - `MidpointListView` (`CMidpointListView`) — the chart view's fourth tab, **Midpoints** (after Details, Aspect Grid and Aspect List): a virtual list of the midpoints of the chart's planets *and* its Ascendant and Midheaven (`Midpoints::Calculate`, so 66 rows for ten planets), built like the aspect list (custom-painted cells, glyph + name for the two points - Z and X for the angles -, the midpoint and its opposite in the element colour (`CAspectListView::GetElementColor`), `Arc`, the midpoint's house, and an **On the midpoint** column naming the points within 1.5 degrees of its axis, with "(opp)" for the far side and the orb). the status bar says "36 of 12345 events". **Show in chart**: a double click on an event calls `IView::ShowMoment(ut, MomentKind)` on the analysed chart's own tab if it is still open (otherwise on a new tab holding the copy the analysis was made from), which puts a transit, secondary progression or solar arc overlay (by the event's analysis) at that moment (`CChartView::ShowMoment`); the tab is activated. **Out of date**: `AspectSettingsChanged` (after Options > Aspects) marks a tab whose analysis looked for aspects as stale in the status bar; **Refresh** then runs it again with the chosen aspects but the orbs as they are now.
  - **Settings** (`AppSettings.h`): `AppSettings` derives from WTLHelper's `Settings` and declares its values with the `BEGIN_SETTINGS`/`SETTING`/`DEF_SETTING` macros (the same way as TotalRegistry's `AppSettings`). One global instance (`g_Settings` in `AstroStudio.cpp`, reached with `AppSettings::Get()`); `WinMain` loads it (`Settings::Load`: `AstroStudio.ini` next to the program if there is one, otherwise `HKCU\Software\AstroStudio\Settings`) *before* dark mode is set up, and `CMainFrame::OnDestroy` saves it. Parts of the program read their values when they are created and write them as the user changes them (in memory; nothing is written until the window closes, so a crash loses the session's changes). Kept: window placement (`MainFrm`/`Run`, ignored if the place is off every monitor), dark mode (-1 until the user chooses: the system's), the status bar, the last house system, the chart view's step count/unit/interval, and the ephemeris toolbar states, step, bodies and extras. **Not** kept: the ephemeris start date (a month before today), transits, Live/Auto. The recent files list is separate (`HKCU\Software\AstroStudio\Recent Document List`, WTL's). Setting names must not be the name of a type used inside `AppSettings` (`StepUnit` clashed with the enum, hence `ChartStepUnit`), and `DEF_SETTING` reads bools as `int`. To add one: `SETTING(...)` + `DEF_SETTING(...)` in `AppSettings.h`, read it where the thing is created, write it where the user changes it.
  - `Interfaces.h` — cross-view contracts: `IMainFrame` (what views can call on the frame) and `IView` (what the frame can call on a tab page: `PageActivated`, `ProcessCommand`). New views should implement `IView`; new frame-level operations should be added to `IMainFrame`.
  - `ViewBase.h` (`CViewBase<T, TBase>`) — CRTP base every tab view derives from; wires up `IView::PageActivated`, idle-driven toolbar UI updates (`CAutoUpdateUI`), and self-deletion on `WM_DESTROY`/`OnFinalMessage`. New tab views should derive from this rather than reimplementing the plumbing.
  - `NetworkHelper` / `WinHttp` — WinHTTP-based lookups (e.g. external IP, geocoding-ish info) used to fill in `ChartInfo` (location/timezone) for "chart for now" style birth data.
  - `AstroFont` / `DefaultFont` — embeds/loads `res\HamburgSymbols.ttf` (the zodiac/planet glyph font) so it renders without being installed system-wide — see commit history for why (avoids requiring a global font install).
    - **`Helpers::LoadAstroFont` loading the font twice is not redundant.** `AddFontMemResourceEx` registers the face with GDI, which is what `CFont`/`CreatePointFont` lookups by name need; DirectWrite cannot see that registration, so `D2DResources` builds its own font collection from the same embedded resource (in-memory font loader + font set builder). Don't "simplify" either away.
    - The glyph tables in `DefaultFont.cpp` must cover their whole enum. `Planet` runs to Vesta (21) while HamburgSymbols originally stopped at Chiron (16), so the last five read past the end. A `static_assert` now ties the planet table's length to `Planet::NumPlanets`, so adding a body fails to compile until it has a glyph. Codes come from the "INDEX #" column of `HamburgSymbols.pdf`.
  - `PlanetSpacer` — layout helper to avoid overlapping planet glyphs when several planets cluster together on the wheel.

## Conventions

- Views communicate with the main frame only through `IMainFrame`/`IView`, not concrete types — keep new cross-view interactions going through those interfaces.
- `AstroCore` must stay free of WTL/Direct2D/UI includes; calculation logic belongs there, drawing/UI logic belongs in `AstroStudio`.
- Dark mode is handled via `WTLHelper`'s `WTLHelper::InitDarkMode()` / `ThemeHelper`; the app toggles it at runtime (`ID_OPTIONS_DARKMODE`) — UI code should get colors from the theme helpers rather than hardcoding them where dark-mode correctness matters.
  - WTLHelper detours `GetSysColor`/`GetSysColorBrush` in dark mode. Never hand out the DarkMode library's own brushes from that detour: callers assume a system brush isn't theirs to delete, and the shell's AutoComplete (it starts as soon as the user types in a file dialog's File name box) deletes the `COLOR_3DFACE` one. The library then paints with a dead handle and every control created afterwards, edit boxes and combos included, comes out light. The detour has its own brushes, validated on each call (`SafeBrush`).

## Gotchas

- Keyboard messages reach a page's dialog only if it handles `WM_FORWARDMSG` and passes it to `IsDialogMessage` (see `CChartView::OnForwardMsg` and `CChartDetailsView::OnForwardMsg`); the details view's Apply is its default button, so Enter applies.
